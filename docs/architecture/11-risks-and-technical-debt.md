# 11. Risks and Technical Debt

## Risks

<!-- Known technical risks, ordered by priority -->

| Risk | Probability | Impact | Mitigation |
| ---- | ----------- | ------ | ---------- |
| In-memory, non-persistent game and leaderboard state | High (any restart/redeploy loses state) | High if ever run as more than a single local/demo instance | `GameSessionStore` (`Services/GameSessionStore.cs`) and `LeaderboardStore` (`Services/ILeaderboardStore.cs`) hold all state in a `ConcurrentDictionary` with no backing store. An app restart or deploy silently drops every in-progress game and the entire leaderboard, and the app cannot scale horizontally or run multiple instances without sticky sessions, since nothing is shared/externalized. Externalize to Redis/SQL (or similar) if multi-instance deployment or state durability is ever needed; until then, document this as a single-instance, best-effort-persistence constraint. |
| Antiforgery/CSRF protection disabled on all gameplay POST handlers | Medium if deployed beyond local/trusted use | Medium — no sensitive data or accounts exist today, so exploitation impact is currently low, but the gap would become serious if accounts/sessions carry any real identity or value later | `Pages/Index.cshtml.cs` applies `[IgnoreAntiforgeryToken]` at the `IndexModel` class level, disabling CSRF protection for all its handlers (`Start`, `NewGame`, `HardDrop`, `Input`, `Release`). Re-enable antiforgery tokens (wire the standard Razor Pages antiforgery token into the client POSTs in `wwwroot/js/site.js`) before exposing the app beyond local/trusted use, or explicitly document the trust boundary if it stays local-only. |
| Unsynchronized in-place mutation of a shared `GameSession`/leaderboard state across concurrent requests | Low today (single local user per session in practice) but increases with any real concurrent/multi-tab usage | Medium — could produce surprising gravity jumps, double-applied ticks, or inconsistent leaderboard reads/writes under race conditions | `GameSessionStore.Replace`/`Get` and `LeaderboardStore`'s dictionary operations are atomic, but the `GameSession` object itself (mutated via `Tick`, `Lock`, `Hold`, etc. in `Domain/GameSession.cs`) and leaderboard entries are not guarded by any lock once retrieved — two concurrent requests against the same session id (e.g. a stalled connection retried, or multiple tabs) could interleave mutations on the same in-memory object. Add a per-session lock (e.g. a `SemaphoreSlim` keyed by session id) around the read-mutate-write cycle, or make `GameSession`/leaderboard updates atomic via a copy-and-replace pattern, if concurrent access becomes a realistic scenario. |

## Technical Debt

<!-- Known technical debt items -->

| Item | Description | Effort | Priority |
| ---- | ----------- | ------ | -------- |
| No automated CI/CD pipeline | No `.github/workflows/*` exist (confirmed via directory search) — the build and the local-only test suite under `tests/infosupport-tetris.Tests/` never run automatically on push/PR, so regressions can be merged without any automated check. | Small–Medium (a basic `dotnet build`/`dotnet test` workflow is a short-lived task; adding deploy stages later is larger) | High — this is cheap to fix and directly protects against regressions as the game grows |
| No production deployment/hosting configuration | No Dockerfile, docker-compose, or other hosting config exist; the app only runs via `dotnet run` per `Properties/launchSettings.json`, i.e. local-dev-only. There is no defined path to actually host this anywhere. | Medium (containerizing an ASP.NET Core app is routine, but hosting/config/secrets decisions add scope) | Medium — not urgent while the project stays local/demo, but blocks any real deployment |
| Leaderboard feature is spec-complete but UI-incomplete (specs 009–011) | `docs/specs/009-submit-score.md`, `010-view-leaderboard.md`, and `011-highlight-my-run.md` describe submitting a score, viewing a leaderboard, and highlighting the player's own run. The domain/service layer exists (`Domain/CompletedRun.cs`, `Domain/ScoreAward.cs`, `Domain/LeaderboardEntry.cs`, `Domain/PlayerName.cs`, `Services/ILeaderboardStore.cs`, `Services/ScoreSubmissionService.cs`, wired into `Pages/Index.cshtml.cs`), but there is no `Pages/Leaderboard*` page or any leaderboard UI reachable from `Pages/Index.cshtml` — a player can never actually view the leaderboard or see their run highlighted in the running app. | Medium (backend logic already exists; mainly needs a new Razor page + navigation + highlighting UI) | Medium — a known, scoped gap rather than a surprise, but it leaves three specs without a user-reachable feature |
| No HTTP-level/integration test coverage | All test files under `tests/infosupport-tetris.Tests/` (e.g. `GameSessionStartTests.cs`, `GameOverTests.cs`, `GravityTests.cs`, `HoldPieceTests.cs`, `LineClearAndScoringTests.cs`) exercise the `Domain`/`Services` layer directly as unit tests; none reference `WebApplicationFactory` or drive `Pages/Index.cshtml.cs`'s POST handlers over HTTP (confirmed via search — no matches for `WebApplicationFactory` anywhere in `tests/`). Regressions in routing, model binding, antiforgery behavior, or the page handlers themselves would not be caught by the existing suite. | Medium (requires adding the `Microsoft.AspNetCore.Mvc.Testing` package and a handful of `WebApplicationFactory`-based tests) | Medium — valuable once the page/handler surface stabilizes, but not blocking while domain logic is the main source of bugs |
